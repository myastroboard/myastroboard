# Update

This guide covers common update workflows for MyAstroBoard.

## Update Published Image

```bash
docker compose pull --policy always
docker compose up -d --force-recreate
docker image prune -f
```

Check running version:

```bash
docker exec myastroboard cat /app/VERSION
```

## Update Local Development Build

```bash
git pull
docker compose down
docker compose up -d --build
docker image prune -f
```

## Backup Before Updating

Data is persisted in `data/`, but a backup is still recommended:

```bash
cp -r data data.backup
```

## Upgrading to 1.7 (database)

1.7 moves the data from JSON files to a SQLite database. The first start does the
migration on its own: it archives the 1.6 files into `data/backups/pre-1.7-<date>.zip`,
imports them, checks them, and only then removes them. If anything goes wrong, nothing is
removed and the instance shows a maintenance page until the cause is fixed - see
[DATABASE.md](DATABASE.md#upgrading-from-16).

The migration is one-way: to go back to 1.6 afterwards, unzip the `pre-1.7` archive into
`data/` before starting the 1.6 image (changes made since the upgrade are not in it).

## Rollback to a Previous Version

```bash
docker compose down
docker pull myastroboard/myastroboard:v1.0.0
docker compose up -d
```

## Application Version

MyAstroBoard release version is managed in the root `VERSION` file.
Update this only after validating compatibility with application behavior,
API outputs, and scheduler expectations.

## Catalogue Data Pipeline

MyAstroBoard now uses the SkyTonight/PyOngc-based catalogue pipeline.

When catalogue behavior changes upstream, refresh generated data with:

```bash
python scripts/build_skytonight_catalogue.py
```

Then commit updated generated artefacts if they are tracked.
