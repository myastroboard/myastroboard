# 🚀 Release Process

This guide explains how to publish a new version of MyAstroBoard, including creating releases and publishing Docker images.

## 📋 Prerequisites

- Write access to the repository
- Git installed locally
- Understanding of [Semantic Versioning](https://semver.org/)

## 🏷️ Versioning Strategy

MyAstroBoard follows [Semantic Versioning](https://semver.org/):

- **MAJOR** version (x.0.0): Incompatible API changes, breaking changes
- **MINOR** version (0.x.0): New features, backwards-compatible
- **PATCH** version (0.0.x): Bug fixes, backwards-compatible

## 📦 Release Process

### Step 1: Prepare the Release

1. **Ensure all changes are merged** to the main branch:
   ```bash
   git checkout main
   git pull origin main
   ```

2. **Check `CHANGELOG.md`**: the `## [Unreleased]` section at the top of
   [CHANGELOG.md](../CHANGELOG.md) is what becomes the GitHub release notes - it should already
   be up to date, since every `feature/`/`fix/` PR is required to add its own entry there (see
   [CONTRIBUTING.md#changelog](../CONTRIBUTING.md#changelog)). Fix anything that reads like a
   novel before tagging - it goes into the release notes as-is.

3. **Update the VERSION file**:
   ```bash
   # Edit the VERSION file with the new version number
   echo "0.2.0" > VERSION
   ```

4. **Review and test changes**:
   - Run all tests: `pytest --cov=backend tests/`
   - Build locally: `docker compose build`
   - Test the application thoroughly

5. **Commit the version change**:
   ```bash
   git add VERSION
   git commit -m "Bump version to 0.2.0"
   git push origin main
   ```

### Step 2: Create a Git Tag

Create and push a version tag. The tag **must** follow the format `v*.*.*` (e.g., `v0.2.0`):

```bash
# Create an annotated tag
git tag -a v0.2.0 -m "Release v0.2.0"

# Push the tag to GitHub
git push origin v0.2.0
```

### Step 3: Automated Build and Release

Once you push the tag, the GitHub Actions workflow will automatically:

1. ✅ **Trigger** the `docker-publish.yml` workflow
2. ✅ **Build** the Docker image
3. ✅ **Publish** the image to Docker Hub with multiple tags:
   - `myastroboard/myastroboard:v0.2.0` (specific version)
   - `myastroboard/myastroboard:v0.2` (minor version)
   - `myastroboard/myastroboard:v0` (major version)
   - `myastroboard/myastroboard:latest` (if on main branch)
4. ✅ **Create** a GitHub Release, with release notes built from `CHANGELOG.md`'s
   `## [Unreleased]` section (plus the commit list and Docker pull commands)
5. ✅ **Archive the changelog**: the `post-release-cleanup.yml` workflow then opens a PR that
   moves `## [Unreleased]`'s content into a new dated `## X.Y.Z (YYYY-MM-DD)` section and resets
   `## [Unreleased]` back to the empty template - review and merge that PR to close out the
   release

### Step 4: Verify the Release

1. **Check the GitHub Actions workflow**:
   - Go to: `https://github.com/myastroboard/myastroboard/actions`
   - Verify the "Build and Publish Docker Image" workflow completed successfully

2. **Verify the Docker image**:
   ```bash
   docker pull myastroboard/myastroboard:v0.2.0
   docker images | grep myastroboard
   ```

3. **Check the GitHub Release**:
   - Go to: `https://github.com/myastroboard/myastroboard/releases`
   - Verify the new release appears with auto-generated notes

4. **Test the published image**:
   ```bash
   # Pull and run the new version
   docker run --rm myastroboard/myastroboard:v0.2.0 cat /app/VERSION
   ```

## 🔄 Manual Workflow Trigger

You can also manually trigger the Docker build workflow without creating a release:

1. Go to: `https://github.com/myastroboard/myastroboard/actions`
2. Select "Build and Publish Docker Image"
3. Click "Run workflow"
4. Select the branch and click "Run workflow"

> [!NOTE]
> Manual triggers will build and publish the Docker image but **will not** create a GitHub release.

## 📝 Release Notes Best Practices

Release notes are generated automatically from `CHANGELOG.md`'s `## [Unreleased]` section (see
Step 1 above) plus the commit list and Docker pull commands - there's normally nothing to write
by hand at release time. The real editing happens *before* tagging, in the PRs that add their
CHANGELOG.md entry: keep each bullet to one or two lines (see
[CONTRIBUTING.md#changelog](../CONTRIBUTING.md#changelog)), and use the right subsection
(`### Features`, `### Fixes`, `### Breaking changes`) so it lands in the right place both in
`CHANGELOG.md` and in the generated release notes.

If a release still needs manual editing after creation (a migration note, a known issue found
after tagging, contributor shout-outs):

1. Go to the release page
2. Click "Edit release"
3. Add the extra section below what was generated - don't rewrite the generated Changelog/Commits
   sections by hand, fix the source in `CHANGELOG.md` instead (via a follow-up PR) so the archived
   entry stays correct too

Example addition:
```markdown
## 📖 Migration Guide
If upgrading from v0.1.x, you need to:
1. Update your docker-compose.yml
2. Run migration script

## 🙏 Contributors
Thanks to @username for their contribution!
```

## 🐛 Hotfix Releases

For critical bug fixes that need immediate release:

1. **Create a hotfix branch**:
   ```bash
   git checkout -b hotfix/v0.2.1 v0.2.0
   ```

2. **Apply the fix**:
   ```bash
   # Make your changes
   git add .
   git commit -m "Fix critical bug in X"
   ```

3. **Update VERSION**:
   ```bash
   echo "0.2.1" > VERSION
   git add VERSION
   git commit -m "Bump version to 0.2.1"
   ```

4. **Merge to main**:
   ```bash
   git checkout main
   git merge hotfix/v0.2.1
   git push origin main
   ```

5. **Tag and release**:
   ```bash
   git tag -a v0.2.1 -m "Hotfix v0.2.1"
   git push origin v0.2.1
   ```

## 🔙 Rolling Back a Release

If a release has issues:

### Option 1: Delete the Release (Recommended for Early Mistakes)
```bash
# Delete the tag locally
git tag -d v0.2.0

# Delete the tag remotely
git push origin :refs/tags/v0.2.0

# Delete the release on GitHub (do this manually via GitHub UI)
```

### Option 2: Create a New Patch Release
If users have already pulled the image, create a fix:
```bash
# Fix the issue
echo "0.2.1" > VERSION
git add VERSION
git commit -m "Fix issue in v0.2.0"
git push origin main

# Create new release
git tag -a v0.2.1 -m "Fix for v0.2.0"
git push origin v0.2.1
```

## ❓ Troubleshooting

### Workflow Fails to Trigger
- Ensure the tag follows the `v*.*.*` format
- Check that you pushed the tag: `git push origin v0.2.0`
- Verify GitHub Actions is enabled in repository settings

### Docker Build Fails
- Check the workflow logs in GitHub Actions
- Verify the Dockerfile is valid
- Ensure all dependencies are available

### Release Not Created
- Check that the tag starts with `v` (e.g., `v0.2.0`)
- Verify the workflow has `contents: write` permission
- Check GitHub Actions logs for errors

### Image Not Published
- Verify GitHub Packages is enabled
- Check repository permissions for GITHUB_TOKEN
- Ensure the workflow completed successfully
